## What changed for users

- **A class that needs a room, placed in a window kept for online courses, is a publish
  warning.** The owner's rule (2026-07-28, `DEFAULT_LAB_SLOTS`) is that only online
  courses meet in the three online-only windows: nothing in the estate is open in the
  evening. Until now a lab dragged to 19:30 was saved with no word anywhere. Now the
  publish check names it:

  | en | ar |
  |---|---|
  | CS114 S1 meets in Online 2 (Sun 17:40–19:20), a window kept for online courses. | تجتمع CS114 S1 في «عن بُعد 2» (الأحد 17:40–19:20)، وهي فترة مخصصة للمقررات عن بُعد. |

  - It is a **warning**: it never blocks publishing, and no write is refused for it.
    A manual move into a window answers 200 as before (owner rule: a manual move is
    never refused for a clash).
  - The classic page says it in the Publish dialog, under "Warnings that do not block
    publishing", in English and Arabic, with "Open board" when it is on another board.
    The pair, the window and the times are each isolated, so Arabic never reverses them.
    A default window ("Online N") is named in the page's language (Arabic «عن بُعد N»);
    a label the department typed is shown as typed, isolated, and never as markup.
  - Split view's readiness console shows the server's English sentence, as it shows
    every other readiness item (split's language is stage 4, SPL-14).
  - The readiness endpoint counts it in `summary.warnings`.
  - The card's ring and the Issues row are D3a's (D-7). MRI is not touched (owner
    decision 2026-10-23).
- **An online course is never marked**, in a window or in a daytime column (Q2's default
  (a)).
- **The board read says which courses are online for the board** (`online_course_codes`),
  placed or not, so a page can tell an online course before its first section is placed
  ((f); D3a's `placeOnline()` reads it). Nothing on the page reads it yet.
- **A time written with a digit from another script is no time on the server, as on the
  page** ((c)). Before, the server read an Arabic-Indic or full-width digit in some
  positions ("٩:30", "1٠:50") as 09:30 or 10:50, while the page read no time and parked
  the meeting. Nothing in the interface sends such a time: the slot editor converts
  Arabic digits before it saves. A no-break space around a time still reads as before.

## Server

`core/services/timetable_slot_config.py`:

- `_TIME` reads ASCII digits (`[0-9]`), as the pages' `SERVER_TIME` does (JavaScript's
  `\d` is ASCII). `\s` stays Unicode on both sides; `re.ASCII` would have narrowed it
  too, which the critique warned of.
- `drawn_column(day, start, end, lecture_slots, lab_slots)`: the column the grid draws a
  meeting in, or None when it is parked. A teaching day, then the **first** column of the
  meeting's kind (a lab runs more than 80 minutes) whose start is the meeting's start,
  which is the renderer's own rule (`firstColumn` in `_renderSingleGrid`).
  `is_on_grid` now asks it, so the two cannot drift; its answers are unchanged (the
  shared case table, both sides).
- `online_window(...)`: the online-only window the grid draws a meeting in, or None:
  `{label, day, start, end}` (the window's label, or its `start-end` when it has none;
  the meeting's day and times as the grid reads them).

`core/services/timetable_workspace.py`, `check_publish_readiness`:

- A last stage: each placement of the scenario that `online_window` puts in a window,
  whose course is not online for its board (`OnlineCourseLookup`, the rule the room
  checks and every placement's `is_online` use) and has no course meeting policy (an
  English bundle has its own table), is one warning item:

  ```
  {"code": "online_window_room_class", "board_id", "board_label", "count": None,
   "params": {"placement_id", "course_code", "section", "day", "slot_label", "start", "end"}}
  ```

  with the English string `Board 'Term 2': CS114 S1 meets in Online 2 (SUN 17:40-19:20),
  a window kept for online courses`.
- Ordered by board (display order, then id), day, start, course, section and id, after
  every other stage. The docstring lists the code with the others.
- **No new query.** It reuses the scenario's placements (already read with their
  sections), the scenario row, and the online lookup the room checks have filled. Pinned
  by a query-count test; measured on 662–666 (below).

`core/timetable_workspace_views.py`, the board read (`/ops/tw/boards/<id>/`):
`online_course_codes`, sorted, from the request's existing `PlacementPayloadContext`
lookup (no new query when the board has placements; one when it has none).

## Deviations from the plan (with evidence)

1. **The code is `online_window_room_class`, not `ONLINE_WINDOW_ROOM_CLASS`.** Every
   readiness item code is lower case: the 11 in `check_publish_readiness`'s docstring
   (`no_boards` … `cross_board_conflicts`) and the page's `READINESS_ITEM_TEXT` keys.
   Upper case is the vocabulary of HTTP error envelopes (`SECTION_LABEL_IN_USE`,
   `PUBLISH_BLOCKED`). One vocabulary with two cases would make every consumer guess.
   **D3a reads `online_window_room_class`.**
2. **The item also carries `placement_id`.** The plan's params name the meeting by course,
   section, day and time. D3a must ring the card and point the Issues row at the meeting;
   with the id it reads the server's verdict instead of recomputing the rule on the page
   (D-7: "one rule, read by every page").
3. **The page got words, although server-only was preferred.** Without them the Publish
   dialog would print the code itself: `readinessItemText` falls back to
   `item.message || item.code`, and no readiness item carries a `message`. Measured in
   jsdom: mutant `page_no_words` shows `online_window_room_class` in the dialog (red, 5
   tests). The words are the plan's own table.
   - Observation, not changed here: the comment above `READINESS_ITEM_TEXT` says an
     unknown code "falls back to the server's English sentence". It falls back to the
     code, because the items never carry the sentence. A tab opened before a deploy that
     adds a code would show the code until reloaded. D5's shared publish flow is the
     place to pair each item with its sentence (`warnings[i]`).
4. **The plan's digit test cannot catch the defect.** "`١٠:٠٠` is off-grid" was already
   true at the base: `[01]?` and `[0-5]` are ASCII, so a time whose every digit is
   Arabic-Indic never matched. The defect is a time with a non-ASCII digit where `\d`
   stands. At the base, `_minutes` read "٩:30", "1٠:50", "10:5٠", "۹:30" (Eastern
   Arabic-Indic) and "９:30" (full width) as 570, 650, 650, 570 and 570, and
   `clean_slot_rows` saved "٩:30" as `09:30`. The tests use those five; the plan's line
   stays as a test too. The shared grid case table gains "1٠:50" (off the grid) and a
   no-break-space case (on), so the server and the page are pinned to one answer.
5. **The [probe] line about 665 was wrong in two ways.**
   - The list is the board's programme set's online courses, placed or not (as (f)
     asked: "per board programme set"), not the budget's: 11 codes on every 665 board
     (GS101, GS102, GS103, GS104, GS111, GS112, GS151, GS152, GSE1, GSE2, GSE3). The
     budget's five GS/GSE courses (GS103, GS104, GS112, GS152, GSE2) are all in it.
   - **IS482 is not online for 665's boards, and is correctly absent.**
     `programme_requirements` marks IS482 online for CYP only (AI, DS, IS, CS and COE
     have it on campus), and 665's boards are DS,AI,AI2,DS2. 665 places IS482 S1–S3 on
     Term 10 in lecture columns with rooms, and the payload's `is_online` is false for
     them, as the room checks have always decided. The triage count of "6 online
     courses" took a course online anywhere as online here.
6. **"In a window" is the grid's column, not an overlap of times.** Online 1 starts at
   15:50, inside Lab 4, the 14:45 and 16:00 lecture columns and before Lab 5 ends. An
   overlap rule would warn about ordinary daytime classes: on the QA copy it flags 19,
   20, 30, 33 and 33 meetings on 662–666 (135 in all, in Lab 4, Lab 5 and the 14:45 and
   16:00 lecture columns), where the column rule flags 0 (`probe_overlap.py`). A meeting
   off the grid is in no window: the page already lists it under its table (offGrid).
   The column rule also keeps the warning on the card that D3a draws in the "Online
   only" table.
7. **Not changed: a range can wrap after its dash.** In the Arabic dialog at 1440×790 the
   line breaks inside "19:30–21:10" after the dash, as any range on the page can. The
   reading order stays right (measured: `measure_wrap.py`, line 1 ends "الخميس", then
   "19:30–"; line 2 starts at its right edge with "21:10"). A no-break range is a page-wide
   matter for D1. After review, D1's spec in the record carries the rule, this line among
   its sites (see "After review").

## After review

One review (APPROVE, three non-blocking findings). Each is fixed as the reviewer proposed;
none changes code, so the tests, mutants and probes above stand as they were run.

1. **The record still wrote the code in upper case.** The D-7 row, B4's own spec and
   D3a's spec in `docs/TIMETABLE-WORKSPACE-UI.md` named `ONLINE_WINDOW_ROOM_CLASS`, so a
   D3a builder reading its spec would look for a string the server never sends. All
   three now say `online_window_room_class`; B4's spec line lists `placement_id` with the
   other params and points at deviations 1 and 2, and D3a's line says the page reads the
   ring and the Issues row from `params.placement_id` instead of recomputing the rule.
   `git grep ONLINE_WINDOW_ROOM_CLASS` now finds it only in this note, where deviation 1
   and this paragraph quote the plan.
2. **An Arabic time range can wrap after its dash** (deviation 7). Left to D1, as the
   reviewer advised, because the same break can happen at every range on the page: the
   fix is one shared rule, not a local exception in one line. D1's spec had no such
   rule, so the record's D1 entry now carries it:
   - `timeRangeText(start, end)` and `timeRangeHtml(start, end)` in `shared-utils.js`,
     with U+2060 WORD JOINER after the dash. UAX #14 allows a break after an en dash,
     and the joiner forbids it. It must be a character, not CSS, because many ranges
     are plain text (`<option>` labels, `aria-label`s, announcements, the readiness
     list). `isolateTimes` inserts it too.
   - The range sites at B4's tree. These are the `isolatedText` ranges, this warning's
     included (PAGE:1718, 3439, 5021, 5088), the hand-written isolate ranges, the Issues
     rows' bare range and the `<bdi dir="ltr">` ranges.
   - Two [CI] lines and two mutants. One is a range scanner over the page; the other is
     a Chrome case in Arabic at 1440×790 with Verdana that keeps this warning's
     "19:30–21:10" on one line.
3. **`?v=66` skips 64 and 65.** No change: any value above 63 busts the cache. The
   Assets table now says what the merger must do. Once the stack and every parallel PR
   that bumps `page-timetable-workspace.js` have merged, bump it once more, past the
   highest value on master (D-20).

The orchestrator's copy of the plan (`scratchpad/stage3/plan.md`) is outside this
worktree and still has the upper-case code in D-7, B4 and D3a, and no range rule in D1.
The committed record is the corrected copy.
