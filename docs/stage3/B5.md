# Stage 3 · B5 · Compress JSON (As built)

Branch `feat/tw-s3-b5-gzip-json`, from `0568d69` (the top of the A1 #189, B2 #190 and B1 #191
stack). Plan: stage-3 plan §3 "B5", decision D-14 (compress JSON only: a subclass of Django's
`GZipMiddleware` filtered to `/ops/tw/`, `application/json`, at least 1 KB, never file
responses; Django's BREACH mitigation kept). Audit item F15.

## What changed for users

- **In production, nothing changes yet (after review).** The middleware sits behind a switch,
  `TIMETABLE_WORKSPACE_JSON_GZIP`.
  - The switch is off by default.
  - `render.yaml` keeps it off, and the blueprint contract pins that value.
  - Render's own pages say its load balancers already compress app responses with Brotli and
    gzip (see "After review"). If that holds for `/ops/tw/` JSON, production's browsers already
    receive these answers compressed.
  - Turning it on in production waits for the host gate below.
- **With the switch on, the workspace's JSON answers travel gzipped.** When the browser accepts
  gzip (every browser does), an answer under `/ops/tw/` that is JSON and at least 1 KB is
  compressed. The browser decodes it before the page's code sees it, so no script changes.
  Measured on the QA copy, scenario 665, production flags on:

  | Read | Before (bytes) | On the wire now (bytes) | Smaller by |
  |---|---:|---:|---:|
  | Opening the classic page (13 JSON reads) | 459,044 | 30,079 | 15× |
  | Opening split view (12 JSON reads) | 861,137 | 53,181 | 16× |
  | A board, `/ops/tw/boards/2420/` | 67,350 | 2,764 | 24× |
  | Its conflicts | 102,955 | 5,101 | 20× |
  | Quality with the lens, `?lens=1` | 65,628 | 6,726 | 10× |
  | The Place dialog's read for a three-meeting course (CS112 S6, `limit=1000&verdict=1`) | 1,024,949 | 30,616 | 33× |

  The sizes are the browser's own (Resource Timing `encodedBodySize` and `decodedBodySize`,
  `probe_browser.out`, `probe_split.out`). **A gzipped size varies by up to 99 bytes from one
  read to the next.** Django's BREACH padding writes a file name of 0 to 99 random bytes, plus
  its terminating byte, into every gzip header (below). So this table's 2,764 B and the cost
  table's 2,782 B are the same board read, compressed twice. The probe's range for it is
  2,686–2,782 B.
- **Nothing else changes.** The workspace pages (HTML), the exports (XLSX and ZIP), every
  answer outside `/ops/tw/` and every answer under 1 KB leave the server byte for byte as
  before, without a new `Vary` header. With the switch off, every answer does.
- **The MRI page is not touched** (owner decision 2026-10-23). No MRI file changes. Its reads
  go to the same shared endpoints as the classic page (`page-timetable-mri.js:225, 278-281`).
  So where the switch is on, its browser also receives them compressed and decodes them first.
  Keeping them uncompressed would need a rule for MRI alone, which would be MRI work. Nothing
  was probed on the MRI page.

## Server

`config/middleware.py`: `TwJsonGZipMiddleware(GZipMiddleware)`.

- `process_response` first reads `settings.TIMETABLE_WORKSPACE_JSON_GZIP`. Off, it returns the
  response as it came, before the parent can add `Vary`. The switch is read on every response,
  so a changed setting needs no new middleware chain.
- With the switch on, `process_response` asks `should_compress`. Only a yes reaches Django's
  own `process_response`, which adds `Vary: Accept-Encoding`, checks the request's
  `Accept-Encoding` and compresses.
- `should_compress` says yes only when all of these hold:
  1. `request.path_info` starts with `/ops/tw/` (with the slash; `/ops/tw-archive/` is not
     the API). `path_info`, not `path`, so a script prefix would not hide the API.
  2. The response is not streaming. A `FileResponse` is a stream (Django:
     `FileResponse(StreamingHttpResponse)`, `streaming = True`, `django/http/response.py:444-453,
     551`). A stream must reach the browser as it is written, and Django's parent class would
     otherwise compress it.
  3. It has no `Content-Disposition` header (a response that names itself a file is a download).
  4. Its media type is `application/json`, ignoring parameters and case
     (`application/json; charset=utf-8` and `Application/JSON` are JSON;
     `application/json-seq` is not).
  5. Its body is at least 1,024 bytes.
- An eligible answer carries `Vary: Accept-Encoding` even when the client does not accept
  gzip, so a cache keeps the two copies of one URL apart. Any other answer gets no `Vary`,
  because its bytes never depend on that header.
- **The BREACH mitigation is Django's, unchanged.** `GZipMiddleware.max_random_bytes = 100`
  (`django/middleware/gzip.py:16`, Django 5.2.17 as pinned in `requirements.txt`).
  `compress_string` writes a file name of random length (`secrets.randbelow(100)` bytes) into
  every gzip header (`django/utils/text.py:347-359`), so the compressed length does not track a
  secret. There is also no secret to track: the only CSRF token in the workspace is in the HTML
  page (`core/timetable_workspace_views.py:561`), which is never compressed.

`config/settings.py`:
- One line in `MIDDLEWARE`, right after WhiteNoise. The response phase runs bottom-up, so it
  compresses after every middleware below it has finished. None of those reads or rewrites a
  body; they set headers and cookies only. So a lower position behaves the same today (mutant
  `wired_last`, below).
- The switch: `TIMETABLE_WORKSPACE_JSON_GZIP`, read from the environment as the other flags
  are, default `"false"`.

`render.yaml` sets `TIMETABLE_WORKSPACE_JSON_GZIP: "false"` on the web service, with the reason
beside it. `scripts/validate_render_blueprint.py` pins that value in `WEB_FIXED_ENV_VALUES`. CI
runs the contract before every deploy, and it refuses a blueprint that turns the switch on or
drops it.

**Off = the default.** To remove B5 entirely, delete its line in `MIDDLEWARE`; the setting, the
`render.yaml` entry and the contract entry can then go too.

**The preview lane is not held longer.** The Place read's view runs under `@preview_lane`, and
its token is released when the view returns (`core/services/request_lanes.py:76-79`). The
middleware compresses after that.

## Deviations from the plan (with evidence)

1. **Each rule has a test that it alone decides.** The plan's mutants were "drop the path
   check (HTML red)" and "drop the type check (XLSX red)". Against those examples alone both
   mutants stay green:
   - The workspace HTML page fails the type check as well as the path check.
   - The XLSX export is a stream as well as not JSON.

   Run as written (`mutants.out`, `mutants_browser.out`):
   - `no_path_check` leaves every HTML-page test green: two server tests and two browser tests.
   - `no_type_check` leaves both XLSX-export tests green, and both browser tests.

   Both mutants go red only on cases where that rule alone decides: JSON outside `/ops/tw/`
   for the path check; for the type check, an HTML error page under `/ops/tw/` (a real 404,
   13.5 KB) and an XLSX workbook held in memory. The plan's own examples stay as tests too.
2. **"Never file responses" is two checks, not `isinstance(response, FileResponse)`.**
   - "Not streaming" covers every `FileResponse`, so a separate `isinstance` check could never
     decide anything (an equivalent mutant). It also covers any other stream, which gzip would
     hold back.
   - Django's own middleware does compress streams. With plain `GZipMiddleware`, the real XLSX
     export comes back gzipped (`plain_django_gzip`, red).
   - Any `Content-Disposition` header is a file too, so a JSON download held in memory would
     not be compressed. No such answer exists today.
3. **The media type is parsed** (parameters and case ignored), and **the path uses
   `path_info`**. Both are pinned (`type_whole_header`, `type_case_sensitive`,
   `path_not_path_info`).
4. **The probe's p50 line is met for the board read, and the Place read is reported beside
   it.**
   - Board read: +0.6 ms over 20 reads (repeats: +2.5 ms over 20 reads, −0.6 ms over 60).
   - The 1 MB Place read: +4.1 ms over 60 reads, which matches its 4.4 ms of compression.
     Over 20 reads it gave +12.5 ms and +0.4 ms in two runs: a localhost p50 over 20 reads
     of an 80 ms read is noisy by about ±10 ms.
   - On localhost the wire saving cannot show. Over a real link the Place read sends 994 KB
     less.
5. **No row in the record's §8.9 table yet.** B1 and B2 add none either. The row goes in when
   the PR lands, so parallel PRs do not edit the record.
6. **Production keeps it off (after review).** The plan wired the middleware on everywhere
   and left the host as a gate in this note (R7, R13). The review pointed out that nothing
   enforced the gate's first step before an auto-deploy. Render documents that its edge
   compresses, which is the outcome that step says not to ship. So the switch defaults to
   off, and `render.yaml` and the contract keep it off until the gate is passed. D-14's
   filter, BREACH padding and cost are unchanged.

## Host gate (production: 0.5 vCPU, 512 MB; unverified, because the host is off limits)

Nobody in this PR may read the production host, so these numbers are not measured there.

**What the code enforces now.** The switch is off in production (`render.yaml`), and the
contract refuses a blueprint that turns it on. **Turning it on is a separate PR that changes
both together**, and that PR brings the evidence of step 1. Until then this PR changes nothing
on the host.

**What to expect if it is turned on.** The host's 0.5 vCPU is a CPU quota. Suppose its core is
two to three times slower than this machine and the quota throttles:
- the 1 MB Place read could cost about 9–13 ms of CPU and up to twice that in wall time;
- a board read, under 1 ms of CPU.

Against that, if nothing in front of the app compresses, the Place read sends 994 KB less.
That is about 160 ms at 50 Mbit/s, and more on campus Wi-Fi.

**The gate.** Someone allowed to read the host runs these steps; the record says who and when.
1. **Check whether Render's edge already compresses.** On production as it is (switch off),
   open the workspace with the browser's network panel and read the response headers of
   `/ops/tw/boards/<id>/`.
   - If `content-encoding` is already `gzip` or `br`, the edge compresses, as Render's pages
     say. Leave the switch off: B5 would only move that CPU onto the 0.5 vCPU host, and swap
     Brotli for gzip. The gate ends here.
   - If there is no `content-encoding`, continue: change `render.yaml` and the contract's
     pinned value to `"true"` in one reviewed PR that cites this step.
2. **After that deploy**, read the same answer again: `content-encoding: gzip`, `vary` includes
   `Accept-Encoding`, and the page draws.
3. **Board read:** 20 reads with and 20 without `Accept-Encoding: gzip`, for example with
   `curl -w '%{time_starttransfer} %{time_total}'` and a staff session cookie. The p50 time to
   first byte rises by at most 10 ms, and the total time does not rise.
4. **Place read** (`limit=1000&verdict=1` for a three-meeting course): the p50 time to first
   byte rises by at most 30 ms, and the total time falls.
5. **Over a working session**, Render's CPU and memory graphs show no new throttling and no
   step in memory, and the log has no new "preview lane full" lines.

If any of steps 2–5 fails, set the switch back to `"false"` (render.yaml and the contract).

## After review

One review round: **APPROVE**, with three non-blocking points. All three are fixed in
`51305b3`.

1. **"Gate step 1 is a before-deploy check that nothing enforces, and merging auto-deploys."**
   Looking for that check's likely answer turned up Render's own pages. The
   [native runtimes](https://render.com/docs/native-runtimes) page lists automatic Brotli and
   gzip compression among the features of every native runtime, and this service runs on one
   (`runtime: python`). The [Render vs Heroku](https://render.com/compare/heroku) page says
   Render's load balancers compress app responses with both. The
   [web services](https://render.com/docs/web-services) page lists Brotli compression. None
   of them names content types, and none was checked against this service. That is
   documentation, not an observation, but it is the outcome step 1 says not to ship.

   So the gate is now enforced in code, not left to whoever merges:
   - `TIMETABLE_WORKSPACE_JSON_GZIP`, off by default and read on every response;
   - `render.yaml` sets it to `"false"`;
   - the blueprint contract pins that value, so turning it on is a reviewed PR with the gate's
     evidence.

   New tests cover the default, the real stack with the switch off, and the blueprint and
   contract. Six new mutants all go red (above). The feature's own tests run with the switch
   on, and every earlier mutant was run again with the same results.
2. **"A wall-clock ceiling (median of 7 under 50 ms) can flake on a noisy CI runner."** The
   budget now holds the fastest of the seven runs, not their median. A busy runner only adds
   time to a run, so one quiet run in seven is enough to pass. A change that slows every
   compression still fails every run: `slow_compression` (60 ms per run) is still red.
3. **"The guard test is not in the mutant table, and the two tables show different gzipped
   sizes for one read."**
   - The guard now pins all 15 cases that the mutants depend on, each with its outcome.
