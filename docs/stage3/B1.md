# Stage 3 · B1 · Server write guards (As built)

Branch `feat/tw-s3-b1-write-guards`, from master `0f2880c`. Plan: stage-3 plan §3 "B1",
decisions D-3 (one section per label in a scenario) and D-17 (no removal of an externally
owned placement).

## What changed for users

- **A section label is used once per scenario, and the server says so.** A planned
  create (`/ops/tw/placements/create-planned/`) of a label already placed on any board of
  the scenario is refused with 409 `SECTION_LABEL_IN_USE`, whichever section holds the
  label (the scenario's own or a global one). The answer carries
  `error.details = {course_code, label, next_free}`, where `next_free` is the first free
  label by the page's own rule. Nothing is written. A label whose placements were all
  removed is free again, so Redo of an undone create still works.
- **Placing an existing section** (`/ops/tw/placements/create/`: a drag from the unplaced
  list, Undo of a Remove, Redo of a create) follows the same rule. The section itself may
  be placed again: on another board (a shared section) or back where it was. It may not
  be placed beside a *different* section of its course that holds the same label.
- **Remove never touches another scenario's section.** `/ops/tw/placements/<id>/remove/`
  answers 409 `PLACEMENT_EXTERNALLY_OWNED` for a section another scenario also places,
  with or without `override`. This check runs before the lock check, as the move,
  pattern-switch and programme-preference endpoints already do.
- **Every caller says the refusal in words, in English and Arabic.**
  - Classic page: a drop (of a planned section, or of an existing one from the unplaced
    list), the Place dialog, the English pattern chooser, Remove, Undo and Redo. Before,
    the toast showed the server's English message.
  - Split view: a drop, a create from the assist, Remove, Undo and Redo. Before, there was
    nothing: these writes have no error handler, so a refusal reached the console only.
    A move refused for a section another scenario owns says the words once; its own
    "Move failed" no longer follows them (after review).
  - A label refusal also reads the budget again on every one of these paths, so the list
    names the free label. The Place dialog moves on to that label and says so in its own
    line.

| Refusal | en | ar |
|---|---|---|
| Label in use | CS112 S1 is already placed in this scenario. The next free section is S6. | الشعبة CS112 S1 موضوعة بالفعل في هذا السيناريو. أول شعبة متاحة: S6. |
| Externally owned | Another scenario owns this section's time and room; change it there. | يملك سيناريو آخر وقت هذه الشعبة وقاعتها؛ عدّلها هناك. |

- The code and label pair is one isolate, and the free label is another, so Arabic never
  shows "S1 CS112" (checked in Chromium; `toast-label-classic-ar.png` in the probe folder).
- The external words are classic's existing `REFUSAL.external`, which the card gate
  already shows for Move and Change room.
- MRI calls neither endpoint. Its only writes are `/move/` (MRI:2682, 2742), and M1
  removes those. Evidence: `grep -n "ops/tw" static/js/page-timetable-mri.js`.

## Server

`core/services/timetable_workspace.py`:

- `SectionLabelInUse(ValueError)` (code `SECTION_LABEL_IN_USE`), with `course_code`,
  `label` and `next_free`.
- `normalise_section_label(value)`: trimmed, upper case, as the page's
  `usedSectionLabels` compares.
- `first_free_section_labels(used, count)`: the page's `freeSectionLabels` rule.
- `placed_section_labels(scenario_id, course_key)`: label → the sections placed under it
  on any board of the scenario. A placement's course is its section's `course_key`, or its
  `course_code` when the key is empty. That is the identity `compute_scenario_budget`
  uses for `used_section_labels`. Keys and labels are normalised on both sides.
- `assert_section_label_free(scenario_id, *, course_key, course_code, label,
  term_section_id=None)`: the one check both views use. `term_section_id` is the section
  being placed again; its own placements do not count against it.
- `create_planned_section_placements`: after `get_or_create`, the section's row is
  re-read with `select_for_update()`, then the label is checked. Both happen inside the
  existing `transaction.atomic()`, before `_drop_stale_workspace_meetings` and before any
  write.

`core/timetable_workspace_views.py`:

- `_section_label_in_use(exc)` builds the 409.
- The create-planned view catches `SectionLabelInUse` before its generic `ValueError`
  mapping.
- The create view checks with `term_section_id=ts.id`, after the board-availability check
  and before any write.
- The remove view checks `external_shared_section_ids` after the published check and
  before the lock check.

## Client

- **Classic** (`page-timetable-workspace.js`, `?v=63`):
  - `serverRefusalWords(error)`.
  - `twFetch`'s toast says those words as a **warning**. Any other refusal is still the
    server's message as an error.
  - `commitPlannedCreate` returns every refusal's code, and the drop reads the budget
    again on a label refusal. The drop of an existing section (`/placements/create/`)
    hears the code through `_onError` and reads the budget again too (after review).
  - `placeRefused` handles `SECTION_LABEL_IN_USE` like `PLACEMENT_DUPLICATE`: it moves to
    the next free label. When the dialog was left, the label words go where the user is.
  - The English chooser and `runHistoryAction` (through `applyHistoryAction`'s new
    `refused` callback) read the budget again on a label refusal.
- **Split** (`page-timetable-workspace-split.js`, `?v=140`):
  - Its own `serverRefusalWords` (the same words) and `sayServerRefusal(body)`.
  - `api()` calls `sayServerRefusal` for a write that has no `onError`. Every create and
    remove path is such a write: `createPlannedPlacementFromMeetings`, `doCreate`,
    `doCreatePlanned`, `doRemove` and `doRemoveApi`.
  - A label refusal reads the sidebar budget again.
  - `api()`'s `_worded` option tells a caller that the refusal was said. The move
    (`movePlacementToSlot`) uses it to skip its own "Move failed" (after review).
  - Other refusals stay console-only, as before. E1 owns split's error handling.

## Deviations from the plan (with evidence)

1. **The place-existing endpoint is guarded too.** The plan named create-planned only
   ("one server caller"). D-3 says labels are unique per scenario, and `/placements/create/`
   can break that in two reachable ways:
   - A global section is dragged from the unplaced list while one of the scenario's own
     sections holds its label.
   - Undo of a Remove runs after another tab gave the label to a new section.

   The section itself is never refused. Pinned by
   `test_placing_the_same_section_again_is_never_refused` (mutant
   `create_view_counts_itself`).
2. **N-7 is narrower than the plan says.** Over HTTP, create-planned already runs under
   `guard_manual_scenario_write`, which takes `select_for_update` on the scenario row
   (`scenario_write_scope`, `core/services/timetable_mutation_guard.py:116-137`). Two
   requests on one scenario were therefore already serialised, and the HTTP race was
   closed. The service's own row lock still ships, for any direct caller.
   - The PostgreSQL test that pins the row lock drives the service, from two threads on
     two connections. The first holds its transaction open after its check until the
     second has checked, or for 3 s.
   - A second test races two HTTP requests (201 and 409). It stays green with the row lock
     removed, because the scenario lock holds; that is the equivalent mutant argued below.
   - A new section's insert is already serialised by the unique index, so the race test
     uses the shape where it is not: the label's section exists with no placements left
     (the Redo case).
3. **The words differ from E1's table.** E1 has "S1 is already placed in this scenario.
   Use S4."; B1 says "CS112 S1 is already placed in this scenario. The next free section is
   S4."
   - "Use S4" is wrong for Undo and Redo, which cannot choose a label.
   - A toast needs the course.
   - The Arabic follows the same shape.
4. **Two copies of the words** (classic and split), not one shared module. This is a
   global-first deviation.
   - The plan already names their shared homes: D5's `timetable-remove-flow.js` for the
     external words and E2's `timetable-section-labels.js` for the label words.
   - A third module now would be one those PRs must dissolve, and the orchestrator
     expected no new asset.
   - The test "classic and split say the same words…" pins the two copies against each
     other in en and ar (mutants `split_arabic_external_drift` and
     `split_pair_isolated_per_part`).
   - **Hand-off (after review).** E2 and D5 delete both copies (`serverRefusalWords` in
     both pages, and split's `ltrIsolate`) in favour of their shared modules, and delete
     the parity test with them. E2's acceptance should say so: 0 definitions of
     `serverRefusalWords` in the two page scripts. Both copies now carry a comment naming
     the other copy, the parity test and the PRs that replace them.
5. **The toast tone is a warning, not an error.** A rule refused the write and nothing
   failed. This matches the card gate's warnings for the same external words.
6. **The order of checks is unchanged.** A create that fails the pattern rule (400
   `FULL_SECTION_PATTERN_REQUIRED`, or another 400) is refused for that before the label
   is checked. The label check needs the transaction and the row lock, so it runs last.
   The probe hit this first: CS112 needs 3 meetings.
7. **Existing tests changed.**
   - `test_a_section_still_placed_elsewhere_in_the_scenario_keeps_its_rows` described
     exactly the write B1 forbids. It is now
     `…_is_never_created_again`, and asserts the refusal, the rows and the placements.
   - jsdom F3 and F6 used `PLACEMENT_EXTERNALLY_OWNED` as an arbitrary refusal to pin
     `twFetch`'s handler contract. That code is now worded, so they use
     `VALIDATION_PLACEMENT`. The contract they pin is unchanged.
8. **Not in B1** (owned elsewhere in the plan):
   - words for `PLACEMENT_LOCKED` (E1, D5);
   - split's `override: true` (E1);
   - hiding Remove on external and locked cards (D5).
   - **Split cannot act on `next_free` until E2** (after review). Split still proposes
     `S{used+1}` (`createPayloadFromBudgetRow`). When a course has a gap (S1 and S3
     placed, for example after S2 was removed), every split create of that course is
     refused with "The next free section is S2", and split has no way to choose S2. Before
     B1 the same create wrote a second S3. Until E2 moves split onto the shared
     `freeSectionLabels`, place such a section from the classic page. On the QA copy no
     budget row is in this state today (0 on 662–666, `after-review/probe_review.py`); it
     arises after a Remove of a middle section.
   - Split's room assignment and programme-preference control pass their own error
     handler, so a section another scenario owns still shows the server's English message
     there (an error toast). That was so before B1; E1 owns split's error handling.
9. **Latent edge, not refused.** A scenario's own section can be placed only by another
   scenario: it is not on this scenario's boards, so its label is free here. A create then
   adds placements to a section another scenario places.
   - This is reachable only through legacy data: the place-existing endpoint refuses
     another scenario's section (`section_is_available_to_delivery_board`), and a planned
     create makes the scenario's own.
   - The QA copy has 0 such sections (probe below).
   - `test_a_section_placed_by_another_scenarios_board_keeps_its_rows` pins today's
     behaviour.
   - Follow-up: refuse it as externally owned if it ever appears.
10. **Latent edge, not refused: the course-identity seam** (after review; pre-existing).
    The label guard matches a course by its normalised `course_key`, the identity the
    budget uses, as D-3 says. Scenario sections usually have a composite key
    (`CS112::PROGRAMMING_I`); registrar sections have the bare code. So a placed registrar
    `CS112 S1` would not hold S1 against a planned `CS112::PROGRAMMING_I S1`, and the
    budget would not count it either.
    - Unreachable on today's data. On the QA copy, 344 of 348 scenario sections have a
      composite key, 0 of 1148 global sections do, and 662–666 place 0 global sections.
    - Follow-up for the deferred backlog, next to the course-identity work (#151/#152): a
      future scenario that places registrar sections next to planned ones could get two
      S1s.
